### Root cause of every C-side variance failure: the oracle always builds its thumbnail branch

Suspect work in the logs pointed at the C's own numbers. Measured directly: the archived C oracle
calls `add_thumbnail_branch` on the single guard `route_id[0] != '\0'`
(`native/archive/c-engine/src/gst_pipeline.c:883-885`) and takes the route id from **argv only**
(`:707-715`) — it has no `preview` key and zero `getenv` in `src/`. The Rust engine gates the same
branch on `"preview": true`, and the harness deliberately omitted that key. So **every earlier
benchmark compared C-with-thumbnail against Rust-without**.

A 2-minute standalone probe (`probe_oracle_thumbnail.py`, route id `bench-probe` vs `""`, harness's
own init JSON and ffmpeg workload) isolated it:

```
thumbnail on  (route_id non-empty): RSS 72.2 MB, CPU 8.0 %, "Thumbnail: Branch ready" present
thumbnail off (route_id "")       : RSS 21.5 MB (flat, cv 0.0003), CPU 6.0 %, branch absent
```

The branch therefore cost **50.7 MB and ~2 CPU-%**, and its internal state varied between runs
(the 2026-10-20 morning run had one C rep at 36.8 MB while the other two sat at 72.4/72.3 MB, and
that single rep was the entire CV failure for `srt-1080p25-5m`). That is what made three workloads
`inconclusive` while all 42 metrics passed. The `"thumbnail": true` field in
`workloads/srt-thumbnail.json` existed but was read by **nothing** — the intended thumbnail-enabled
workload had never been wired, so it too compared unlike pipelines.

### Harness fix (make the comparison like-for-like)

`benchmarks/migration/scripts/run_benchmark.py`:

- `build_init/2` adds `"preview": true` for workloads that set `"thumbnail": true`.
- `build_plan/4` → `build_plan/5` with `engine_name`; it blanks the **C's** route-id argument for
  workloads that do not ask for the branch (the only lever the frozen oracle has) and keeps the Rust
  argv as-is.
- Plans now carry `engine_arg`, `handshake`, `socket_token`, `thumbnail`; the lifecycle uses those

- New `_assert_branch_shape/4` asserts `"Thumbnail: Branch ready"` is present **exactly** when the
  workload asked for it, for both engines — so this class of drift cannot return silently.
- The wrong comment claiming "the C engine only builds its thumbnail chain when the config asks for
  one" was replaced with the measured truth.
- `benchmarks/migration/README.md` documents the asymmetry and states that results recorded before
  the change are not comparable with results after it.

## Key Decisions & System Constraints Resolved

- **The fair numbers are the honest ones.** At pure passthrough the engines are near-identical
  (CPU 0.995-1.040, RSS 0.938-1.049, throughput 1.0000-1.0007). The previously reported
  "Rust uses 0.26-0.88x the memory" was the C paying for a thumbnail branch the Rust never built.
  A route with a preview costs ~72 MB on **both** engines.
- **No further benchmark rerun for the two inconclusive workloads.** Both causes are structural
  (µs-scale quantization; an immutable oracle's nondeterminism). The honest remedies are decisions:
  a harness rule for sub-millisecond CV, and/or a versioned oracle with an explicit preview flag
  (the same "version the oracle" decision already recorded for the int32 loss-counter blindness).
- **Root steps stay with the user.** `sudo -n` fails on this host and no sudoers drop-in was written;

- **A measurement run needs a quiet box and no release.** The user's live routes (PLTV, SPOTV2) hold

## Correction: the SPOTV2 `audio-pids` reading (false positive — my error)

The live route showed `audio-pids` rendered as `~c"578"` while `PLTV` showed `[201, 202]`, and the
2026-10-17 log had recorded SPOTV2 as `audio [578]`. Reading the term with
`inspect(value, charlists: :as_lists)` gave `[53, 55, 56]` — the ASCII codes of `5`, `7`, `8` — which
looked like a PID string split into bytes, i.e. a real bug in the metadata path. It is not.

The trail, in order, and where it went wrong:

1. The engine's reported values were stable (`video-pid 52`, `audio-pids [53,55,56]`) from t≈4 s and
   never corrected — consistent with a one-shot PAT/PMT latch.
2. A standalone engine against the same source reproduced them, with a udpsink capturing the TS the
   same connection carried. That capture "showed" video PID 256 / audio 258,259,260 — the disagreement
   that started the hunt.
3. A faithful transcription of `parse_pmt` over that capture always produced the *correct* answer, for
   every alignment; the repo's own `ts_probe_real_capture` diagnostic agreed.
4. The capture was the flaw: `ffmpeg -c copy -f mpegts` re-muxes, and ffmpeg's mpegts muxer assigns
   its own PIDs (program 1, PMT PID 4096, video 0x100, audio 0x102+). Step 2's "ground truth" was
   ffmpeg's output, not the source.
5. Raw byte capture of the same connection, no ffmpeg in the path (python UDP `recv`):
   `PAT program 152 → PMT PID 2049`, entries `type=0x1b pid=52`, `type=0x86 pid=54`,
   `type=0x03 pid=53`, `pid=55`, `pid=56`. Exactly what the engine reports — including the correct
   exclusion of the `0x86` (SCTE-35 style) stream from `audio-pids`.

So `video-pid 52` / `audio-pids [53,55,56]` is correct data for this stream, `~c"578"` is only
`inspect/1`'s charlist sugar, and the Audio PID tile is right. The 2026-10-17 finding "the source
serves a different mux per caller" has the same root cause — one source, one mux, and an ffmpeg
capture whose PIDs belonged to ffmpeg. Both records are corrected here, and the pitfall in
`docs/skills/gstreamer-pipeline-diagnostics/SKILL.md` now names the mechanism (the rule against
trusting an ffmpeg capture existed since that session; the reason it bites was missing).

Raw evidence kept on the host: `/tmp/spotv2_raw.ts` (22 MB, the connection's own bytes).

## 2026-10-21 01:30-02:10 UTC — health windows, hysteresis, and "what now?" in every event

Measured the warning flood first: the ring held 500 events over 6.8 h (18:47-01:35) of which 254
were `health_changed` at warning — PLTV 112, SPOTV2 142 — every single one tripped by loss, never by
RTT (max 0.636 ms against a 300 ms threshold). 1 s windows were 2.0-7.1 % while cumulative loss over
those 6.8 h was 0.17-0.25 %: short bursts SRT was already retransmitting, reported as degraded
routes every ~3 minutes.

- **`lib/blackgate/route_health.ex`** — health is judged on `loss-window-10s-pct` (sustained loss
  over ~10 s); `warning` additionally needs `loss-streak >= 3` consecutive reports; `critical` fires
  immediately at 10 %. New public `degraded?/1` (loss or RTT past threshold, before hysteresis, so
  the registry can count the streak) and `transient_burst?/1`.
- **`lib/blackgate/route_stats_registry.ex`** — rolling 10 s history kept in its own ETS key
  `{:loss_window, route_id}` (samples + streak + burst-log timestamp, trimmed to 10 s / 30 samples),
  published as `loss-window-10s-pct` and `loss-streak`; burst events rate limited to one per 10 s;
  `put_stats/3` takes an optional `now` as a test seam; `delete_stats/1` drops the history row;
  health messages now append their numbers.
- **`lib/blackgate/event_guidance.ex`** (new) — one English "what now?" line per event type plus a
  per-verdict line for `health_changed`, appended by `EventLog.log/4` and stored in
  `metadata[:action]`. "none — …" when nothing is needed, an instruction when it is, nil for
  bookkeeping (`route_started`, `route_stopped`). New test `event_guidance_test.exs` reads the call
  sites out of `lib/**/*.ex` and fails if an event type ships without an action.
- **Severity audit (all 36 call sites)**: `ffmpeg_missing` was logged with `:error`, which is not in
  `@severities` — it raised `FunctionClauseError` from inside the logging path (verified), so a host

## 2026-10-21 03:00-03:20 UTC — Duo 2 connector mapping: half-duplex profile unlocks all four SDI ports

The operator corrected a wrong assumption of mine: the card is a DeckLink Duo 2 with **four** SDI
connectors, and seeing only some of them is not a fixed input/output split — it is the connector
mapping, i.e. the card's duplex profile. The agent was told to learn from `feat/decklink-duo2`
(read-only; the branch must not be touched), which is a pre-Rust C-era branch.

What the branch contains (read via `git show`/`git grep` on `origin/feat/decklink-duo2`, no checkout):

- `web_app/src/utils/sdiPorts.js` — the real Duo 2 map, with the comment "Blackmagic driver
  enumerates the 4 physical connectors out of order: io0→SDI 1, io1→SDI 3, io2→SDI 2, io3→SDI 4":
  `DEVICE_TO_SDI = {0: 1, 1: 3, 2: 2, 3: 4}`, `SDI_TO_DEVICE = {1: 0, 2: 2, 3: 1, 4: 3}`,
  `SDI_PORT_OPTIONS` = SDI 1..4 → device 0, 2, 1, 3.
- Help text: "DeckLink Duo 2 port number. This card provides 4 SDI channels (0-3)."
- The branch's `native/` is C only (no Rust engine) and its SDI sinks set only `device-number`; so
  four-port operation there depended on the card already being in a half-duplex profile.
- `rust-migration` instead hardcodes the Quad 2 eight-port map (`OutputPopover.jsx` device map,
  `RouteDestEdit.jsx` "8 SDI channels (0-7)" text, archived `docs/archive/SDI_FIXES.md`), which is
  the inconsistency the operator saw in the UI.

Measured on the card (`gst-launch-1.0 videotestsrc → decklinkvideosink`, 1080p25):

| profile on the sink | device 0 | 1 | 2 | 3 |
|---------------------|----------|---|---|---|
| none (driver default) | OK | OK | not-negotiated | not-negotiated |
| `four-sub-devices-half` | rejected outright (card has two sub-devices) |
| `one-sub-device-half` / `two-sub-devices-full` | rejected |
| **`two-sub-devices-half`** | OK | OK | OK | OK |

So with the half-duplex profile all four device numbers accept playback: **four SDI outputs**. The
kernel log agrees with the branch's mapping (io0 = "DeckLink Duo 2 (1)", io1 = "(3)", io2 = "(2)",
io3 = "(4)"). The profile partly persisted after the first successful set (device 2 worked in a later
run without the property, device 3 did not), so the reliable approach is for the engine to set the
profile on every SDI sink rather than relying on card state.

The current Rust engine sets no profile at all (`grep -rn profile native/rust/engine-gst
native/rust/engine-sdi` is empty), which is why only two of the four ports work in Blackgate today.
Follow-ups: port `sdiPorts.js` (four ports + the Duo 2 wording) into `rust-migration` without
touching the branch, and have the engine pass `profile=two-sub-devices-half` for SDI sinks.
