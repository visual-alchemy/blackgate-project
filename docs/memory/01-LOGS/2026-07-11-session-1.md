# Session Log: 2026-07-11-session-1

## 📋 Session Overview
- **Topic:** RTMP source video framerate mismatch and loopback macroblocking diagnostics.
- **Goal:** Resolve `~25 fps` display error and troubleshoot output stream corruption (macroblocks) on RTMP caller routes.

## 🔍 Key Findings & Actions

### 1. Framerate Detection Fix
- **Diagnosis:** `ffprobe` verified stream runs at 50 fps. C engine parsed raw SPS headers before decoding and default H.264 framerate was hardcoded to `25 fps` (inferred) due to missing VUI parsing.
- **Fix:** Modified `on_thumbnail_pad_added` in [gst_pipeline.c](file:///Users/eldyreynanda/Developer/Antigravity/blackgate-project/native/src/gst_pipeline.c) to query decoder negotiated caps and write true decoded width/height/framerate directly to `video_info` stats struct, setting `fps_inferred = FALSE`.

### 2. Output Macroblock / Stream Corruption Fix
- **Diagnosis:** Captured remote SRT output stream on `192.168.40.61`. Log showed massive H.264 packet loss (`non-existing PPS 0 referenced`, `decode_slice_header error`).
- **Root Cause:** FFmpeg's SRT `latency` parameter is parsed in microseconds (µs), while GStreamer expects milliseconds (ms). The loopback configuration was set to `latency=500`. This configured the FFmpeg loopback sender to a latency of only **500 microseconds** (0.5ms). Any local CPU scheduling delay exceeding 0.5ms caused FFmpeg to instantly drop packets, corrupting the stream.
- **Fix:** Modified `build_ffmpeg_command` in [route_handler.ex](file:///Users/eldyreynanda/Developer/Antigravity/blackgate-project/lib/blackgate/route_handler.ex) to use `latency=500000` (500ms in microseconds), matching GStreamer's receiver latency.

### 3. Verification & Push
- Rebuilt locally via `make -C native`.
- Committed and pushed all changes to origin branch `rtmp-ffmpeg`.
