# Session Log: 2026-07-11-session-1

## 📋 Session Overview
- **Topic:** RTMP source video framerate mismatch diagnosis and resolution.
- **Goal:** Fix why the Web UI reports `~25 fps` for an incoming 50 fps RTMP video source.

---

## 🔍 Key Findings & Actions

### 1. Diagnosis
- **RTMP stream validation:** Running `ffprobe` on the RTMP URL confirmed the actual stream runs at `50 fps` (`r_frame_rate=50/1`, `avg_frame_rate=50/1`).
- **Codebase Root Cause:** The GStreamer C engine uses a raw MPEG-TS demuxer probe (`ts_probe_callback`) to parse SPS headers before decoding. For H.264 streams, it lacks a complete VUI (Video Usability Information) parser, so it hardcoded the inferred default framerate to `25 fps`. This value was written to `video_info` and sent via JSON to the Elixir/React frontend.

### 2. Implementation
- **Fix:** Updated the preview branch callback `on_thumbnail_pad_added` in [gst_pipeline.c](file:///Users/eldyreynanda/Developer/Antigravity/blackgate-project/native/src/gst_pipeline.c) to query negotiated raw video pad caps from the decoder.
- **Update Logic:** When decodebin exposes the decoded raw video pad, the true negotiated/decoded video properties (width, height, framerate, and interlace mode) are extracted and written directly to the `video_info` stats struct, setting `fps_inferred = FALSE`.
- **Outcome:** The frontend now displays the accurate 100% decoded framerate (`50 fps`) instead of the hardcoded default `~25 fps`.

### 3. Verification & Push
- Compiled native binary successfully via `make -C native`.
- Staged, committed, and pushed changes to origin branch `rtmp-ffmpeg`.
