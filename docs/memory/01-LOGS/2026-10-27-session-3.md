## Key Decisions & System Constraints Resolved

- **`sudo` is password-gated again in this session** (`sudo -n true` → `a password is required`) and
  `SUDO_PASSWORD` is NOT in the process environment, so every root step went into ONE script for the
  operator to run (`sudo bash <script>`), which is also the reference's rule for a multi-step privileged
  deliverable. Do not design around an earlier session's non-interactive `sudo`: it is a cached,
  per-invocation fact.
- **The ported Step 7 was deliberately NOT a verbatim copy.** The sibling's step chains
  `tee … && sysctl --system && echo "wrote …"`, and `make install` runs under `set -e`, so a failing `tee`
  would abort the whole install after all the dependencies were installed. This version uses `if`/`||` forms
  only: a failed write or apply is reported in words and the read-back decides the verdict. Proven by
  extracting the recipe into a scratch script and running it under `set -e` in six conditions — values
  already at 16 MB (no warning), low values (WARNING + the exact root commands), `sysctl --system` failing
  (`note:`, install continues, no false warning), no `sudo` binary on PATH (write refused, then WARNING),
  no `sudo` binary and `/etc/sysctl.d` unwritable (`SKIPPED:` + WARNING), and non-Linux (manual message).
  All six: `bash -n` clean, exit 0. `make -n install` exits 0.
- **The deploy script's verification block was rehearsed UNPRIVILEGED against the retained
  `2026.10.27.1` package**, which is the only way to test it without root: signature verifies against
  `/etc/blackgate/update-public-key.pem` ("Signature Verified Successfully"), `release_sha256` in the
  manifest matches the tarball, the packaged `blackgate-updater` sha equals the repo's
  `iso-builder/files/blackgate-updater`, and the release tarball HAS a `blackgate/` wrapper level (which is
  why the updater extracts it with `--strip-components=1`), so the script locates the engine, bundle and
  notes with `find` instead of a hardcoded path. The notes JSON key is **`changes`**, not `changelog`.
- **Which live proof actually needs the new release: only the Elixir/web half.** The deployed
  `2026.10.27.1` already runs today's engine binary (`61feee43…` — the 32 MB sink budget, the preview
  change) and its `RouteHandler` already carries `hls_source` (the `-re` pacing), while it does NOT carry
  `restart_error`/`describe_conflicts`. So the RSS-on-multi-destination and the HLS-pacing measurements can
  be taken on the RUNNING release, with no deploy at all; the deploy is only needed for the refused-restart
  fix, the license-card date and the install step.
