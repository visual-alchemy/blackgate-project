## The finding: RSS grows only where the pipeline decodes

| route | sink shape | RSS 21:54 → 09:30 | growth |
|---|---|---|---|
| 52b09cb6 | SRT → SDI (no network egress) | 456 → 918 MB (13 h) | +462 |
| 52adcad6 PLTV | SRT → SDI + SRT 20000 | 394 → 874 MB | +480 |
| 52af75b6 SPOTV2 | SRT → SDI + SRT 19000 | 386 → 820 MB | +434 |
| 07a7c5fe HLS | HLS → SDI + SRT 18000 | 422 → 746 MB | +324 |
| d4d63560 HLS | HLS → SRT 16000 + 17000 (**no decode**) | 79 → 91 MB | **+12** |

The growth is monotonic hour over hour, and the first half and second half of the run add nearly the same
amount (+233 / +229 MB on 52b09cb6; +260 / +220 on PLTV), so there is no plateau in sight. Engine RSS in
total went 1,740 → 3,450 MB. Threads (44–52) and file descriptors (21–30) stayed constant, so this is not
a thread or fd leak, and `VmData` runs well above `VmRSS` (1,250 MB vs 918 MB), i.e. memory is being
allocated and retained rather than touched.

The discriminator is the pipeline SHAPE, not the protocol: the only engine that stayed flat is the only
one that never decodes (HLS sidecar → SRT passthrough, 6.6 % of one core). Every engine with a decode
branch grows, whether its source is SRT or HLS, and whether or not it has an SRT destination. So the
suspect is the decode path and its buffers — NOT the SRT egress leg, NOT the CDN, NOT the Elixir side.

One anomaly inside the trend: `07a7c5fe` jumped 555 → 746 MB between the 00:55 and 01:55 samples after
creeping at ~30 MB/h. The journal in that hour holds only the licence heartbeat, so this reads as a
one-off allocation step (a buffer pool resizing when the HLS feed came back healthy) rather than a second
defect — but it is the reason that route's total is not on the same line as the others.

## Extrapolation, stated as arithmetic and not as a promise

+39 MB/h per decoding engine is ~+940 MB per engine per day. With five engines the box gains roughly
4.7 GB/day against 15 GB of RAM (3.5 GB already held by engines at 09:30, ~12 GB available). That puts
OOM somewhere in the second or third day of an unattended run — which is exactly the question the
customer-facing appliance has to answer, so it cannot be left as "monitor it".

## The next step I would run (needs no DeckLink card)

An A/B that isolates decode from everything else, using two probe engines on spare ports and a synthetic
feed, so the card is never touched:

- A: `ffmpeg testsrc` → SRT → engine **decode → SRT out**
- B: the same feed → engine **copy → SRT out** (the d4d63560 shape)

Measure RSS for 60–90 min. If A grows and B is flat, the leak is provably in the decode path and can be
profiled and fixed without the card and without the live routes. If both are flat, the trigger is
something the live routes have and the probe does not (the SDI sink, the thumbnail/preview branch, or the
dual-source failover wrappers), and the probe gets widened accordingly.

Do not start that experiment while the five live routes are streaming if the numbers are meant to be
attributable — it costs one to two cores and the same box is carrying 45 Mbps of egress.

## Midday: probe A/B verdict, the apt restart, and where the memory actually is

Stage 1 probe (`/home/blackgate/blackgate-trend/ab-decode-probe.sh`) ran 90 min and came back
negative, which is the useful answer:

| arm | shape | RSS 90 min |
|---|---|---|
| A | `preview:true` (avdec_h264 decode branch), SRT in → SRT out | 70.7 → 72.0 MB (**+0.9 MB/h**) |
| B | `preview:false`, no decode anywhere | 21.6 → 21.6 MB (+0.0) |

Both receivers pulled 90 min of video, so flat is flat and not a stall. The live engines grew
+34…+38 MB/h over the same window, i.e. 40× more. **The preview/decode branch alone is not the leak.**
The harness smoke run caught its own bug first: one ffmpeg SRT listener serves one caller, so the
second arm starved in `Connection timeout` — one sender per arm is mandatory.

`smaps_delta.py` then watched three live SDI engines for 25 min: the growth is **`[anon]`**
(+36.3 MB on 263085, +122.6 MB on 263119, +82.4 MB on 246306), never `libDeckLinkAPI.so`. So the
DeckLink driver is innocent; the memory is process heap (GStreamer buffers or glibc malloc arenas).
Both engines carry 4 × ~64 MB anon mappings, the classic glibc `HEAP_MAX_SIZE` shape, so the
candidates are "buffers retained" vs "arenas never returned", and they need different fixes
(code vs `MALLOC_ARENA_MAX`). `arena-watch.sh` now logs the anatomy per engine per minute
(rss, vmdata, threads, anon maps ≥1 MB, anon maps 60–70 MB, heap) to tell them apart from data.

## The half hour after the soak: apt restarted the gateway

At 06:23:29 UTC (13:23 WIB) systemd stopped `blackgate.service` — not a crash and not the operator:
`apt-daily-upgrade.service` had upgraded `libbrotli1` at 06:23:27, and the service was stopped two
seconds later; `Restart=always` brought it back at 06:23:38, all five engines exited 143 with it.
`memsup terminating` / `ArgumentError` / `port_died` in the log are effects of the SIGTERM, not the
cause. Routes do not auto-start by design, so all five came back stopped and the box pushed nothing
until the operator started them at 06:37.

Same hour, before the restart: 06:10:13 `SDI sink 0 failed — continuing without SDI output
(DeckLink device 3)` on 07a7c5fe, then 06:11:26 `Watchdog detected SDI playout freeze (60s no
frames)`. A device that drops out and comes back points at cabling/PCIe, not software.

**Appliance rule this produced: an unattended apt upgrade must never be able to interrupt a running
gateway.** The operator was given `sudo systemctl disable --now unattended-upgrades`; if security
patching is kept, needrestart has to exclude `blackgate.service`.

## The egress doubling was retransmission, and it died with the restart

Between 03:36 and 06:23 UTC the NIC showed 87–104 Mbps TX while the panel's five destinations summed
to 47.8 Mbps. `tcpdump` settled it: 45,270 of 5 s packets went to a single host, the wired iMac at
192.168.40.182 (all five SRT clients live there). Panel then: dropped 0.00 % everywhere (1,096 packets
out of 22.7 GB on 16000/17000), retx 32.47 % / 32.66 % on the two sinks of the HLS route, 12.78 % on
18000, 2.16 % / 3.08 % on the SRT-fed legs. The small 5.7 Mbps streams retransmitted 15× more than the
21 Mbps one, so this was never link saturation. After the 06:23 restart TX is back to 44 Mbps with the
same clients and the same sources — so the excess was retransmission, not a second copy of any stream.
