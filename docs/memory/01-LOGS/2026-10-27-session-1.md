## Release-notes delivery: what was written, and why a static file was NOT kept

`iso-builder/release-notes.txt` honours a hand-written notes file, and one was created for
`2026.10.27.1` listing only the 7 real fixes — then deleted again before committing, deliberately:
the file is static while `scripts/write-release-notes.sh` is shared by the packager AND the ISO
builder, so the next build of this branch would ship today's list as its changelog. The notes are
therefore built from commit subjects, which is honest per build.

The real gap is in that fallback: `write-release-notes.sh` runs `git log --pretty='- %s' -12`, so the
deployed release's notes carry the last 12 commits regardless of whether they are IN that release
(this build listed 13 lines of which 7 were real: chore/docs commits from this session, plus
`0303b16`/`69b9ac4` which the attached release did not actually change). The correct fix is a
generated delta — `<deployed version>` → HEAD — which needs the deployed release's commit marker and
was NOT implemented. Proposal, not a defect.

### A verified gap, contrary to the skill's own note

- `7e281fb` (`make install` raises the SRT socket buffers itself) — **this branch's Makefile has NO sysctl
  step at all** (`grep -n "sysctl\|rmem_max" Makefile` → nothing; verified this session). The ISO's
  `blackgate-firstboot.sh` writes `/etc/sysctl.d/90-blackgate.conf`, so an APPLIANCE is fine, but a
  `git clone` + `make install` host gets nothing — and the failure shape is the bad one: SRT loses
  datagrams at high bitrate and the logs blame the network. The skill is NOT wrong about this: it lists

  branch ships no in-repo way to set the buffers, so a fresh host depends on an operator remembering a
  line from a doc. This box is correct only because the operator set the values by hand
  (`net.core.rmem_max = net.core.wmem_max = 16777216`).

## Candidate #1 implemented — a refused restart is no longer reported as success

Commit `f05cb46` on `feat/port-from-rust-gateway` (NOT deployed; the box still runs `2026.10.27.1`).

- The three call sites are fixed (`route_controller.update/2`, `destination_controller` create/update/delete):
  `maybe_restart/2` reports `%{"restarted" => false, "restart_error" => …}` when `Blackgate.restart_route/1`
  returns `{:error, reason}` — which it does for a listener port or SDI connector another route holds, because
  `restart_route/1` runs the claim check BEFORE it stops anything.
- The sentence has ONE implementation: `SdiClaims.describe_conflicts/1` ("SDI 1 is in use by <route>; port N is in
  use by <route>"), now shared by the Start refusal and both controllers, so the frontend's existing conflict
  pattern matches all three paths.
- Frontend: both edit forms show the refusal as a warning instead of a success toast; the pattern moved to
  `web_app/src/utils/sdiPorts.js` as `RESTART_CONFLICT_RE` so `RouteItem.jsx` can adopt it too (not done — its
  Start path reads `error.message`, which is already a plain sentence).
- TEST SEAM, deliberately: `Blackgate.engine_process_route_ids/0` now reads `:persistent_term`
  `{Blackgate, :running_route_ids}` when a test sets it. Without a way to fake "these engines are up" the gate had
  NO refusal test at all, and none can exist (a test may not spawn an engine). Nothing in the running system sets
  the key; the test erases it in `on_exit`.
- Proof: `test/blackgate_web/controllers/destination_restart_refusal_test.exs` (2 tests) drives real PUT/DELETE
  requests where another route holds the listener port and asserts `restarted: false` plus the named holder.
  `mix test` = 271 tests, 0 failures. `npx eslint` on the three touched web files reports only PRE-EXISTING
  no-unused-vars lines (verified against the committed versions).
- Why the ALLOWED-restart path is not pinned by a new test: it stops the route and starts a real engine
  (`{:error, :invalid_source}` in a test). It stays covered by `destination_controller_test.exs` (stopped route →
  `restarted: false`) and by the live gateway.
