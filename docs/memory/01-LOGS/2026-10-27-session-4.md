## Root cause of the egress-loss badge

Not the network. `Blackgate.RouteHealth.evaluate/1` judged egress on the **lifetime** ratio of
`packets-sent-lost / (packets-sent + packets-sent-lost)` per `srtsink` and flipped to
`network_loss_egress` at 2 %.

`packets-sent-lost` on an srtsink is SRT's `pktSndLossTotal` — packets the peer reported
missing, most of which the sender retransmits and delivers inside the negotiated latency. The
counters are lifetime figures, so one burst (a client connecting, a hiccup) stayed in the
ratio for as long as the engine lived. That is exactly the reported symptom: badge amber,
picture clean.

The ingest leg had already been fixed for this class of bug (`loss-window-10s-pct` plus a
three-report streak, see the comments in `route_health.ex`); egress had not.

## The fix (commit `03a9dc6`)

- `RouteHealth.egress_loss?/2`: severe (10 %) fires at once, anything from 2 % has to hold
  `@warning_streak` (3) reports. `nil` — no history yet — is never evidence of loss.
  `egress_threshold/0` exposes the shared threshold so the registry does not duplicate it.
- `RouteStatsRegistry.update_egress_window/3`: per-destination growth across the same ~10 s
  window as the ingest leg, history in ETS under `{:egress_window, route_id}`, dropped by
  `delete_stats/1` so a restarted route does not inherit a stale window.
- Published keys: `egress-loss-10s-pct`, `egress-streak`, `egress-loss-destination`,
  `egress-loss-cumulative-pct` (the lifetime ratio, kept as evidence, no longer the verdict).
- Health events now open with `egress loss 3.2% over 10 s on destination 1 (lifetime 0.4%)`
  so the event explains itself.
- Web: `DestinationStats` shows `<n> lost (x.xx%)` and `<n> retx` per destination, and the
  `network_loss_egress` tooltip no longer implies a broken picture.

Tests: 4 new in `route_health_test.exs` (lifetime-ratio regression, single-second, severe
without streak, plus the windowed positive), 2 new in `route_stats_registry_test.exs`

## Found while verifying: every stop or destination change crashes its own HTTP request

Route `07a7c5fe` gained a second destination (SDI dev 3 + `srt://0.0.0.0:18000`) at 10:10:21
and came back up correctly with the new sink — but the request process died mid-flight:

    [error] Ranch listener BlackgateWeb.Endpoint.HTTP ... had its request process #PID<0.5064.0>
    exit with reason {{{:noproc, {GenServer, :stop, [#PID<0.2222.0>, :normal, :infinity]}},
                       {BlackgateWeb.Endpoint, :call, [...]}}

Mechanism, confirmed by reproducing the exit reason in isolation:

    {:ok, sup} = Supervisor.start_link([], strategy: :one_for_one)
    Supervisor.stop(sup, :normal); Process.sleep(50)
    Supervisor.stop(sup, :normal)
    # -> exit {:noproc, {GenServer, :stop, [pid, :normal, :infinity]}}   (identical tuple)

`Supervisor.stop/2` on an already-dead pid **exits**; it does not return an error. That is
exactly what `Blackgate.clear_stale_route_entry/1` does at `lib/blackgate.ex:192`: `stop_route/1`
stops the tree on line 129, then judges it unusable (obviously — it just stopped it), then the
fallback path stops the same dead pid a second time. The exit propagates out of `stop_route/1`
→ `restart_route/1` → the controller action, so the response is never written.

Not a `.3` regression: 11 occurrences in the journal since 04:06, every single one preceded by
`GET /api/routes/<id>/stop` (7), `POST /api/routes/bulk-action` (1) or
`POST|PUT /api/routes/<id>/destination` (3). `grep`ed over the whole journal, all 11 are on that
path — but the path is not always fatal: 4547 route stop/start/destination/bulk requests were
logged in the same period, so this is a **race**, not a certainty (0.24 %). It needs the `:syn`
entry to still be present when `clear_stale_route_entry/1` looks it up, moments after
`stop_route/1` killed the tree; usually `:syn` has already dropped it and the second
`Supervisor.stop/2` is never reached. The `.2..…3` diff touches `route_health.ex`,
`route_stats_registry.ex`, their tests, two JSX files, `release-version` and
`resource_trend.py` — nothing on the restart path.

Side effect worth its own note: because the request process crashes, Logger dumps the whole
`Plug.Conn`, **including the `authorization: Bearer *** header**, into journald in plaintext.
Fixing the crash removes that path; until then the operator's API token sits in the journal.

Proposed fix (not applied, operator's call): guard the second stop in
`clear_stale_route_entry/1` with `Process.alive?/1` and treat the already-dead case as success.

## The fix for it (commit `b86e50b`)

`Blackgate.stop_route_tree/1` — public, so both stop paths and the tests judge the same thing —
treats a tree that is already down as the state the caller asked for: `Process.alive?/1` first,
and the `{:noproc, …}` exit caught for the window where the tree dies between the check and the
call. Both `Supervisor.stop/2` call sites (`stop_route/1` and `clear_stale_route_entry/1`) now go
through it. Only two call sites existed, so this closes the class.

`test/blackgate/route_stop_test.exs`: 5 tests, **all 5 red without the fix** (verified by stashing
`lib/blackgate.ex` and re-running — including the full `stop_route/1` path, which reproduced the
exit in the harness), 281 green with it. `mix format --check-formatted` clean.

Second stop on an id that is no longer registered anywhere answers `{:error, :not_found}` — the
pre-existing answer for a missing route, reached through the `find_route_tree/1` fallback. Pinned
in a test so the shape stays an answer rather than a crash.

Root cause of the plaintext token, for the record: Logger dumps the whole `Plug.Conn` — headers
included — whenever a HTTP request process exits abnormally, and Ranch writes that through
Logger. Fixing the crash removes this instance; any future controller crash would dump it again.
Redacting the header needs a `:logger` filter or a custom formatter, which is its own decision.

### Probing gotchas, so the next session does not repeat them

- The engine writes telemetry to a unix socket from `stats_socket_path/1`, not to stdout:
  `$BLACKGATE_STATS_SOCKET` or `/tmp/hydra_unix_sock`, plus `_rust` in `--shadow` mode. A probe
  engine with no override **connects to the live app's socket** and injects records for its
  route_id into the production registry — v1 did exactly that at 11:10 with route id `unknown`.
  Always export `BLACKGATE_STATS_SOCKET` to a private path.
- The first argv (after an optional `--shadow`) is the route id; without it the engine uses
  `unknown` and prints `Argument 1: unknown`.
- The engine treats stdin EOF as shutdown ("stdin closed … shutting down pipeline"), so a probe
  must hold stdin open (`(cat init.json; sleep N) | engine`), not `cat init.json | engine`.
- A listener srtsink with no caller still reports `bytes-sent-total`, so a non-zero total is not
  evidence that a client is attached; check `connected-callers` per record (14 of 18 in the probe).

## B — every start path is judged, under one lock (`009cdc3`)

- `Blackgate.with_route_lock/1` = `:global.trans({{Blackgate, :admission}, self()}, fun, [node()])`.
  Verified it works on a `:nonode@nohost` node before relying on it, because `mix test` runs
  undistributed.
- `start_route/1` and `restart_route/1` judge the licence **inside** that lock, against the count of
  **live engine processes** (`running_route_ids/0`), not the stored `status`: a dead route counted
  against the licence refuses a start the operator has paid for, and a live one that is missed lets a
  route through. Both judgments and the start happen inside the lock, so two concurrent starts cannot
  each see room for the last slot.
- **A restart is not a new slot**: the route about to be stopped is subtracted from the count, or
  editing the destination of the last covered route would be refused. The judgment still happens before
  the stop, so a refusal leaves the route running on its previous destination.
- Refusal shape: `{:error, {:license, reason}}` → 402 on Start and Restart, carrying the licence's own
  sentence; the bulk action passes that sentence through instead of `inspect`ing it (it is the row the
  operator reads in the "N started, M failed" summary); destination edits report it beside the change.

## A — the pass that stops what the licence no longer covers (`e72810e`)

- `License.capacity_of/1` is now the single answer to "how many routes may run": `max_routes` for a
  licensed key, `trial_max_routes` for a trial, and **0 for every state that is not a licence**
  (expired, unlicensed, or a status a newer server invented). The old `can_start_route?/0` fell through
  to `{:error, …}` only in its final clause; everywhere else an unknown state read as permitted.
- `Blackgate.LicenseEnforcer`: a pass every 10 s and immediately when the licence changes (activate,
  deactivate, heartbeat re-verify). Live engine set, **sorted by route id**, the first `capacity` are

  not once per tick. Taking every stream down over a number this module could not read is worse than
  leaving a route running that the operator can stop by hand; strictness belongs to the admission layer,

- `EventLog.log/4` no longer lets a failed PubSub broadcast take its caller down: the licence check runs

- A gateway with no licence now says so (`license_missing`): critical when the trial window has passed,

## C — sync on demand, a clock floor, and the limits written down (`e40a453`)

- `POST /api/license/sync` + "Sync license now" on the License page: the heartbeat asks every 6 hours
  and only logs the outcome, so a key extended/replaced/revoked could take the better part of a day to
  arrive. A server that cannot be reached answers 422 with the reason and leaves the cached licence in
  use; a gateway on the trial says there is no key to re-check.
- Clock floor: `License.judgement_date/1` keeps the furthest-forward date seen in Khepri
  (`license/clock_high_water`) and judges expiry against it, so setting the clock back cannot extend a
  licence or renew a trial. The trial window is also clamped to a full window, so a first-boot stamp in
  the future cannot compute a longer trial. (First attempt used `:khepri.get([@clock_key])` — a
  double-wrapped path, so the read never matched and the floor silently never held. The two tests that
  move the clock caught it.)
- `docs/license-enforcement.md`: the states and capacities, both enforcement layers, the table of what
  happens on expiry/deactivation/offline/clock rollback/duplicate-store loss, the API, how to fake a
  licence in a test — **and what this does NOT protect against** (unsigned cached payload, root can edit
  the store, activation needs the server, enforcement lives in this codebase). Deterrence, not
  tamper-proofing; worth saying plainly before it is sold as enforcement.
- The License page shows the running route count beside the capacity, because those are the two numbers
  a start is judged by.

## Egress: the badge was reading the wrong counter, and the label said "loss"

### What the operator reported

Three VLC clients on the iMac `192.168.40.182`, same LAN, same VLAN, ports 16000 / 17000 / 18000.
The panel showed:

    16000  4.20 Mbps  2.0 ms  495.57 MB  33,900 lost (9.29%)  33,900 retx  1 client
    17000  4.21 Mbps  2.2 ms  696.26 MB  36,006 lost (9.50%)  36,006 retx  1 client
    18000  3.90 Mbps  1.7 ms  485.78 MB   9,052 lost (2.84%)   9,052 retx  1 client

`lost` and `retx` are the same number, packet for packet, on all three. Both players were clean.

### Why that happens (code + probe, not a guess)

- `packets-sent-lost` is libsrt's `pktSndLossTotal`: the count of packets the PEER reported
  missing. SRT answers every one of those with a retransmission, which is why the retx counter
  matches it exactly. It is a link COST, not damage.
- `packets-sent-dropped` (`pktSndDropTotal`) is what the SENDER gave up on: too late to resend
  inside the negotiated latency, or no room in the send buffer. Nothing recovers those; the viewer
  loses them. That is the only honest loss figure.
- Probe on this box (`~/.hermes/cache/scratch/srt-sink-probe3.sh`, isolated ports 19998/19999, own
  `BLACKGATE_STATS_SOCKET`, route id as argv[1]): a clean 6.2 Mbps listener session reads
  `sent` climbing, `lost` 0, `dropped` 0, `retx` 0. SIGSTOP the receiver so the queue backs up and
  `packets-sent-dropped` starts moving (12 -> 25 -> 39) while `lost`/`retx` stay 0. The two counters
  are independent and both reach the engine (`engine-stats/src/lib.rs:556` maps
  `packets-sent-dropped`; `:563` maps the retransmit count).
- The path itself, measured from the box: gateway `192.168.40.254` 200/200 replies, 0 % loss,
  0.12 ms avg; the iMac 200 pings: **3.5 % loss** (5.5 % with 1200-byte payloads), 0.90 ms avg,
  max 10 ms. So the LAN does lose a few percent to that host, SRT recovers all of it, and the
  panel called the recovery "loss".

### What changed (this release, 2026.10.27.7)

- `Blackgate.RouteStatsRegistry`: the egress window now tracks `packets-sent`, `packets-sent-dropped`
  and `packets-sent-retransmitted` per destination. The verdict (`egress-loss-10s-pct` and its
  cumulative twin) is computed from **dropped**. New keys beside it:
  `egress-retx-10s-pct`, `egress-retx-destination`, `egress-retx-cumulative-pct` — the cost, in its
  own number, never mixed into the loss figure.
- `Blackgate.RouteHealth`: the `network_loss_egress` verdict now reads the dropped ratio, so a stream
  that SRT is fully recovering stays healthy. The comment that claimed the two counters were the same
  thing is replaced with the measurement above.
- Event text: "Egress packets dropped on output client connections (SRT gave up, viewers lost them)",
  and health evidence now prints both facts — "egress loss X% over 10 s on destination N (packets the
  sender dropped, nothing can recover them; lifetime Y%)" and "SRT resent Z% on destination N
  (retransmitted inside the latency, so recovered; lifetime W%)".
- UI: Destination Statistics shows **N dropped (x.xx %)** in red only when non-zero, and
  **N retx (y.yy %)** beside it in neutral colour, each with its own tooltip. `HealthBadge` and the
  routes list label read **Egress Dropped**, not "Egress Loss". The routes-list tooltip says
  "Packets Dropped" and reads `packets-sent-dropped` for a destination leg.
- `docs/TROUBLESHOOTING.md`: a section that separates dropped from retx for an operator, with the two
  ping commands that tell last-hop loss from gateway loss.

### Correction — this box runs in UTC, so a WIB-looking `--since` queries the FUTURE

`/etc/timezone` is `Etc/UTC`; `20:40` in a `journalctl --since` means 20:40 UTC, i.e. 03:40 WIB the next
morning, and returns `-- No entries --` for a service that is logging normally. Every journal read from
this box must use UTC (`date -u`, or `--since "@<epoch>"`). Any earlier "the journal showed nothing"
claim built from a WIB-looking timestamp — including the "40 minutes clean after `.7`" report — was an
empty query, not a quiet box. The soak watcher is immune because it passes epoch seconds.
