## Root cause of the egress-loss badge

Not the network. `Blackgate.RouteHealth.evaluate/1` judged egress on the **lifetime** ratio of
`packets-sent-lost / (packets-sent + packets-sent-lost)` per `srtsink` and flipped to
`network_loss_egress` at 2 %.

`packets-sent-lost` on an srtsink is SRT's `pktSndLossTotal` — packets the peer reported
missing, most of which the sender retransmits and delivers inside the negotiated latency. The
counters are lifetime figures, so one burst (a client connecting, a hiccup) stayed in the
ratio for as long as the engine lived. That is exactly the reported symptom: badge amber,
picture clean.

The ingest leg had already been fixed for this class of bug (`loss-window-10s-pct` plus a
three-report streak, see the comments in `route_health.ex`); egress had not.

## The fix (commit `03a9dc6`)

- `RouteHealth.egress_loss?/2`: severe (10 %) fires at once, anything from 2 % has to hold
  `@warning_streak` (3) reports. `nil` — no history yet — is never evidence of loss.
  `egress_threshold/0` exposes the shared threshold so the registry does not duplicate it.
- `RouteStatsRegistry.update_egress_window/3`: per-destination growth across the same ~10 s
  window as the ingest leg, history in ETS under `{:egress_window, route_id}`, dropped by
  `delete_stats/1` so a restarted route does not inherit a stale window.
- Published keys: `egress-loss-10s-pct`, `egress-streak`, `egress-loss-destination`,
  `egress-loss-cumulative-pct` (the lifetime ratio, kept as evidence, no longer the verdict).
- Health events now open with `egress loss 3.2% over 10 s on destination 1 (lifetime 0.4%)`
  so the event explains itself.
- Web: `DestinationStats` shows `<n> lost (x.xx%)` and `<n> retx` per destination, and the
  `network_loss_egress` tooltip no longer implies a broken picture.

Tests: 4 new in `route_health_test.exs` (lifetime-ratio regression, single-second, severe
without streak, plus the windowed positive), 2 new in `route_stats_registry_test.exs`
(window vs lifetime, streak gate + the event naming the destination). `mix test` = **276
tests, 0 failures**; `npm run build` succeeds.

Gotcha worth remembering: a test that injects a past `now` must read the ETS row directly —
`get_stats/1` calls it stale and reports `disconnected` regardless of the verdict.

## Found while verifying: every stop or destination change crashes its own HTTP request

Route `07a7c5fe` gained a second destination (SDI dev 3 + `srt://0.0.0.0:18000`) at 10:10:21
and came back up correctly with the new sink — but the request process died mid-flight:

    [error] Ranch listener BlackgateWeb.Endpoint.HTTP ... had its request process #PID<0.5064.0>
    exit with reason {{{:noproc, {GenServer, :stop, [#PID<0.2222.0>, :normal, :infinity]}},
                       {BlackgateWeb.Endpoint, :call, [...]}}

Mechanism, confirmed by reproducing the exit reason in isolation:

    {:ok, sup} = Supervisor.start_link([], strategy: :one_for_one)
    Supervisor.stop(sup, :normal); Process.sleep(50)
    Supervisor.stop(sup, :normal)
    # -> exit {:noproc, {GenServer, :stop, [pid, :normal, :infinity]}}   (identical tuple)

`Supervisor.stop/2` on an already-dead pid **exits**; it does not return an error. That is
exactly what `Blackgate.clear_stale_route_entry/1` does at `lib/blackgate.ex:192`: `stop_route/1`
stops the tree on line 129, then judges it unusable (obviously — it just stopped it), then the
fallback path stops the same dead pid a second time. The exit propagates out of `stop_route/1`
→ `restart_route/1` → the controller action, so the response is never written.

Not a `.3` regression: 11 occurrences in the journal since 04:06, every single one preceded by
`GET /api/routes/<id>/stop` (7), `POST /api/routes/bulk-action` (1) or
`POST|PUT /api/routes/<id>/destination` (3). `grep`ed over the whole journal, all 11 are on that
path — but the path is not always fatal: 4547 route stop/start/destination/bulk requests were
logged in the same period, so this is a **race**, not a certainty (0.24 %). It needs the `:syn`
entry to still be present when `clear_stale_route_entry/1` looks it up, moments after
`stop_route/1` killed the tree; usually `:syn` has already dropped it and the second
`Supervisor.stop/2` is never reached. The `.2..…3` diff touches `route_health.ex`,
`route_stats_registry.ex`, their tests, two JSX files, `release-version` and
`resource_trend.py` — nothing on the restart path.

Side effect worth its own note: because the request process crashes, Logger dumps the whole
`Plug.Conn`, **including the `authorization: Bearer …` header**, into journald in plaintext.
Fixing the crash removes that path; until then the operator's API token sits in the journal.

Proposed fix (not applied, operator's call): guard the second stop in
`clear_stale_route_entry/1` with `Process.alive?/1` and treat the already-dead case as success.

## The fix for it (commit `b86e50b`)

`Blackgate.stop_route_tree/1` — public, so both stop paths and the tests judge the same thing —
treats a tree that is already down as the state the caller asked for: `Process.alive?/1` first,
and the `{:noproc, …}` exit caught for the window where the tree dies between the check and the
call. Both `Supervisor.stop/2` call sites (`stop_route/1` and `clear_stale_route_entry/1`) now go
through it. Only two call sites existed, so this closes the class.

`test/blackgate/route_stop_test.exs`: 5 tests, **all 5 red without the fix** (verified by stashing
`lib/blackgate.ex` and re-running — including the full `stop_route/1` path, which reproduced the
exit in the harness), 281 green with it. `mix format --check-formatted` clean.

Second stop on an id that is no longer registered anywhere answers `{:error, :not_found}` — the
pre-existing answer for a missing route, reached through the `find_route_tree/1` fallback. Pinned
in a test so the shape stays an answer rather than a crash.

Root cause of the plaintext token, for the record: Logger dumps the whole `Plug.Conn` — headers
included — whenever a HTTP request process exits abnormally, and Ranch writes that through
Logger. Fixing the crash removes this instance; any future controller crash would dump it again.
Redacting the header needs a `:logger` filter or a custom formatter, which is its own decision.
