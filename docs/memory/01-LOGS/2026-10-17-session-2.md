# 2026-10-17 Session 2 — duo2 Statistics Port to the Rust Engine (Video Metadata)

## Sprint Goal & Focus

Apply the statistics that exist on `feat/decklink-duo2` to the Rust engine, and
find out why the Dashboard showed no video metadata and why a purely local SRT
route reported degraded metrics.

## What Was Accomplished

### engine-metadata — four defects that hid every video statistic

- **PMT off-by-one.** After `section_length`, `parse_pmt` skipped four bytes
  instead of five (`program_number` 2 + version 1 + section_number 1 +
  last_section_number 1). `program_info_length` was therefore read one byte early
  (240 instead of 0 on a real stream) and the stream loop walked off the packet, so
  **every** PMT failed to parse: no `video-*` keys ever reached the UI. Regression
  tests use the real captured PMT packet plus a synthetic one whose audio PID
  follows the video PID.
- **500-attempt cap removed.** The port invented a per-TS-packet attempt limit and
  printed `VIDEO_STREAM_TYPE:unknown` when it expired. Neither the C nor the lite
  engine has such a limit, and at 15 Mbps the cap expired in ~50 ms — long before
  the first SPS/IDR of a mid-GOP join. The probe now keeps looking until the stream
  yields a header, exactly like C.
- **TS packet resync.** SRT payload boundaries do not line up with 188-byte TS
  packets, so a buffer can start mid-packet; the fixed stride then read a bogus
  PAT/PMT (a live route reported video PID 65/audio 66 from a PMT packet with PID 32
  and a 140-byte adaptation field). `resync_offset()` now finds the first sync byte
  whose next 188-byte step is also a sync — the C `source_ts_probe_callback`
  behaviour, with an extra guard so payload bytes equal to `0x47` are not mistaken
  for a boundary.
- **Emulation-prevention bytes.** H.264/HEVC encoders insert `00 00 03` so an RBSP
  can never contain a start code. The C strips them (`remove_emulation_prevention`)
  before bit parsing; the port did not, so every field after the first escape
  shifted — a live High-profile SPS with two EPBs reported a framerate of
  `2^24` (16777216) instead of 25 fps. Now applied to both the H.264 and HEVC SPS
  paths, covered by a test using that real SPS.
- **duo2 fields ported.** `VideoInfo` gained `fps_inferred`, `video_pid` and
  `audio_pids`; the H.264 parser defaults to 25/1 with `fps_inferred = true` (C
  behaviour, the UI renders inferred rates as `~25 fps`); the PMT parser collects
  every stream entry (no early return at the first video entry) so audio PIDs that
  follow the video PID are not lost.

### engine-stats

- Emits `video-pid` (only when known) and `audio-pids`, and reports
  `video-framerate-inferred` from the new `fps_inferred` field instead of inferring
  it from `fps_num == 0`.

### Elixir

- `unix_sock_handler.ex`: `stats_to_metrics/2` walked every list as if it held
  nested stats maps, so the new `audio-pids` list of integers raised
  `BadMapError` on every report (`Error processing stats: %BadMapError{term: 66}`,
  twice a second). It now recurses only into maps and emits scalars as metrics.
- `route_health.ex`: the `drops_per_sec` check on `sdi_video_stats` is gone (duo2
  parity). Those counts are `videorate` framerate-conversion drops, not hardware
  failures; real failures crash the pipeline and are handled by RouteHandler.

### Web

- `RouteStats.jsx`: video format summary line (`AVC VIDEO FORMAT … 1920×1080p/25 ·
  16:9 · Input 12.158 Mb/s`), Video PID and Audio PID tiles, Received/Lost packet
  tiles, and the duo2 tile names.
- `SystemPipelines.jsx`: uses `systemPipelinesApi.getDetailed()` (endpoint and API
  client already existed) and shows Route, live CPU, RSS, threads and state.
- `HealthBadge.jsx`: warning tooltip said `RTT > 150ms`; the backend threshold is
  300 ms (`@rtt_warning`).

## Follow-up — the "warning" on a purely local SRT route

- **Socket buffers.** `net.core.rmem_max`/`wmem_max` were 212992 (208 KB) on this
  host while AGENTS.md requires 16 MB; at 12-15 Mbps that is ~110 ms of buffering
  against a 2000 ms SRT latency, so bursts overflowed the receive socket. Raised to
  16777216 via `/etc/sysctl.d/90-blackgate.conf` (user-applied; the ISO firstboot
  script writes the same file).
- **Measured before/after** (route Test, 20 s windows of SRT receiver deltas):
  - before (208 KB): 1.287%, 1.452%, 1.867%, 1.668% — average ~1.6%
  - after (16 MB): 0.653%, 0.695%, 0.297% — average ~0.55%
  The control route (PLTV, untouched connection) stayed at 0.1-0.4% throughout.
- **The badge was still "warning" after the fix**, because `route_health` used the
  cumulative `lost / (received + lost)` ratio and the connection-startup burst
  (~2800 packets in the first 30 s) stays in that ratio for the whole life of the
  connection: 3.18% cumulative against ~0.5% steady-state. `RouteStatsRegistry` now
  also publishes `loss-window-pct` (delta over the last report interval, like the
  existing `drops_per_sec`) and `route_health` prefers it, falling back to the
  cumulative value when no window exists yet.
- **Stale stats socket.** Restarting the app twice in quick succession left a second
  node that unlinked `/tmp/hydra_unix_sock`, bound its own socket and died, so the
  path pointed at a dead socket: every new engine got
  `connect: Connection refused (os error 111)` and the Test route crash-looped
  ("Pipeline exited with status 1, entering reconnect mode" every 10 s) while the
  already-connected route kept running. `make start` now refuses to run when a node
  is alive (and removes a leftover socket file first), and `make restart` waits for
  the old node to release its name instead of racing it.

## Live Preview — duo2/quad2 study and the green/macroblock fix

Studied how `feat/decklink-duo2` and `feat/decklink-quad2` build the dashboard
preview. Both use the same design in the C engine:

```
tee → queue (NO leak, 64 MB / 8 s) → tsdemux
     → [video pad] h264parse|h265parse → (H.264: keyframes only) → avdec_h264|avdec_h265
     → deinterlace → videoconvert → videoscale 320x180 → capsfilter
     → 1 fps PTS gate → jpegenc → appsink (sync=FALSE, async=FALSE)
```

- The queue must not shed compressed TS: dropping packets here corrupts transport
  continuity and HEVC reference frames.
- H.264 reaches the decoder only at keyframes (`thumbnail_keyframe_probe` drops
  `GST_BUFFER_FLAG_DELTA_UNIT`): a decoder joining a live TS mid-GOP otherwise
  emits macroblocks and green frames until the next IDR.
- HEVC gets `config-interval=-1` (repeat VPS/SPS/PPS at IDRs) plus
  `output-corrupt=FALSE` / `discard-corrupted-frames=TRUE` on the decoder.
- The 1 fps gate replaces `videorate`, which asserts when decoded frames carry no
  duration (a source reporting an unknown framerate) and kills the pipeline.
- quad2 additionally taps already-decoded SDI frames (one decode for playout and
  preview) and demotes VA-API decoders, whose `interlace-mode="mixed"` output
  fails negotiation downstream of videoconvert/videoscale.

The Rust port used `queue(leaky=downstream, max-size-buffers=2)` + `decodebin`:
on a 13 Mbps feed that queue holds ~2.6 kB ≈ 1.6 ms of transport stream, so almost
every packet was dropped before the demuxer. Measured on the live dashboard:
PLTV preview **83% green pixels** (mean RGB 25,127,22) and Test preview showing a
16-px block grid — both signatures of decoding from a shredded, mid-GOP stream.

`engine-thumbnail` was rewritten to the C design (queue no-leak 64 MB/8 s, explicit
tsdemux + parser + decoder with the keyframe gate, HEVC config-interval and
corrupt-frame handling, deinterlace, 1 fps PTS gate, appsink sync/async off,
bounded `try_pull_sample`). Evidence after deploy:

- PLTV: green pixels 83% → **0%**, mean RGB (188,187,208).
- Test: preview now matches an ffmpeg reference decode of the same source —
  green 21% vs 23% control, identical step-edge profile (5 7 8 10 … 20), no 16-px
  spike. The earlier "blockiness" reading was the content gradient, not blocks.
- Both preview files refresh on the 5 s cadence.

Operational note found while deploying: `bin/blackgate stop` cannot reach a node
whose release directory was wiped by `make build` (its pid file is gone), so
"restarts" silently kept running the old engine. `make stop` now also kills any
surviving release node by pid.

## SPOTV2 could not receive — the stats socket was clobbered by a test run

The source (`srt://192.168.50.42:12999?mode=caller`) was fine: ffprobe/ffmpeg pulled
2.4 MB in 3 s, and once the real blocker was fixed the route reported 10.5 Mbps
healthy with full video metadata (1920x1080 AVC/H.264 High, 25 fps, pid 52,
audio [578]) and a clean preview.

The blocker was the stats socket. Both sides hardcoded `/tmp/hydra_unix_sock`, so
any `mix` task that boots the app — `mix test` above all — bound the same path,
which unlinked the *running release's* listening socket and left a dead file
behind. Every engine started afterwards died instantly:

```
RouteHandler: pipeline: connect: Connection refused (os error 111)
RouteHandler: Pipeline exited with status 1, entering reconnect mode
```

while routes whose engines were already connected kept working. The socket file's
mtime gave it away: 09:41:10 (the gate's `mix test`) instead of the node boot at
09:38:06, and the same pattern at 09:10 earlier in the session.

Fix: the path is configurable and the test environment uses its own.

- `Blackgate.stats_socket_path/0` (config `:blackgate, :stats_socket_path`,
  override with `BLACKGATE_STATS_SOCKET`).
- The release passes it to every engine port; the engine reads
  `BLACKGATE_STATS_SOCKET` (default `/tmp/hydra_unix_sock`) and prints the path it
  failed to connect to.
- `config/test.exs` binds `/tmp/blackgate_stats_<os pid>.sock`, with a regression
  test asserting the test path is never the production one.

## Closing the stats-socket failure class (will a new route work?)

Three levels, all verified against the running release:

1. **Per-environment socket paths.** `config/config.exs` keeps
   `/tmp/hydra_unix_sock` for the release, `config/dev.exs` uses
   `/tmp/blackgate_stats_dev.sock`, `config/test.exs` a per-run path, and
   `config/runtime.exs` honours an operator override (`BLACKGATE_STATS_SOCKET`).
   Verified with `mix run --no-start`: dev → `/tmp/blackgate_stats_dev.sock`,
   test → `/tmp/blackgate_stats_<pid>.sock`, prod → `/tmp/hydra_unix_sock`.
2. **The app refuses to start on a taken path.**
   `Blackgate.Application.assert_stats_socket_free!/1` probes the path and raises
   with an actionable message when a live listener answers, instead of binding and
   silently unbinding it. Verified live: a prod-env node started while the release
   ran printed `/tmp/hydra_unix_sock already has a live listener: another Blackgate
   node is running on this host` and exited; the socket's mtime was unchanged and
   the release socket stayed reachable.
3. **Makefile guards** (earlier in the session): `make start` refuses when a node
   is alive and clears a leftover socket first, `make restart` waits for the old
   node to release its name, `make stop` kills a surviving release node.

End-to-end experiments while the release ran:

- `mix test` → socket mtime unchanged, socket reachable, 0 `Connection refused` in
  the release log (previously every engine started afterwards died).
- `MIX_ENV=dev mix run` → same.
- Route stop/start (a brand-new engine) → connected, healthy, 0 `Connection
  refused`. SPOTV2 came back healthy at 10.3 Mbps.

## Rust engine loses SRT packets where the C engine does not (engine-side, proven)

The user reported that a machine running the blackgate-lite (C) engine shows 0 lost /
0 dropped / 0 retransmitted on `srt://192.168.50.96:10048` while this box shows loss.
That is real, and it is engine-side — not the network path.

Reproduced with both engines on THIS box, same source, same config, same 5-minute
window, both standalone, stdout to files, minimal callers, no SRT errors in either:

```
C engine    (blackgate-lite)  recv=203815  lost=0     dropped=0     retrans=0     rate=13.44 Mbps  rtt=0.816
Rust engine (rust-migration)  recv=203347  lost=5600  dropped=1074  retrans=4740  rate=13.41 Mbps  rtt=0.540
```

Ruled out, each with a measurement:

- **Network path / NIC** — the C engine is clean on the same box, same switch, same
  source. NIC RX errors 0; kernel `RcvbufErrors` flat at 1085 (no receive-buffer drops).
- **Socket buffers** — both engines request the same: `rb24576000` (24.5 MB) receive,
  `tb131072` send (verified with `ss -u -a -m -p` on both processes).
- **Stat field mapping** — Rust reads exactly the C's fields
  (`packets-received-lost/-dropped/-retransmitted`, `rtt-ms`, ...). The C's
  `build_source_stats_json` reads the real srtsrc `stats` structure when present, so
  its zeros are measurements, not the hardcoded fallback in `add_source_probe_stats`.
- **Thumbnail branch** — A/B with `BLACKGATE_NO_THUMBNAIL=1`: 7578 vs 6996 lost. Same.
- **Sink branch** — A/B with `"sinks": []` vs an srtsink: 3574 vs 3554 lost. Same.
- **Source listener backlog** — the final run had no SRT errors on either side, so the
  `Listener's backlog exceeded (5)` seen earlier was a side effect of running several
  probe callers at once.
- **Libraries** — both binaries load the same `libgst*.so` and the same
  `/usr/lib/x86_64-linux-gnu/gstreamer-1.0/libgstsrt.so` (GStreamer 1.24.2).
- **Negotiated latency** — 2000 ms in both (from the SRT stats structure).

What is left: the Rust engine drives the same `srtsrc` element differently. Its
`dropped` counter (SRT-level, too-late/buffer) is nonzero while the C's is 0, and its
`lost` grows with a flat kernel `RcvbufErrors` — consistent with the receiver's flow
control making the source's sender drop, rather than packets being lost on the wire.
Its srtsrc also errors and reconnects at times (`Error on SRT socket: Unknown or
erroneous (0)`, `Listener's backlog exceeded (5)`) where the C's never does.

Next step: dump the `srtsrc` element's effective properties in both engines (or run
both with SRT's own logging) and compare — the pipelines and config are otherwise
identical, so the difference is in how the Rust side sets the element up.

### Property dump: identical

Both engines now print every readable source property with `BLACKGATE_DUMP_PROPS=1`
(Rust: `dump_element_props` in `engine-gst/src/builder.rs`, called from `make_source`;
C: the same block appended to `set_element_properties`, added only in the throwaway
worktree `/tmp/bglite`, never in the blackgate-lite branch).

```bash
{ printf '%s\n' "$JSON"; sleep 14; } | BLACKGATE_DUMP_PROPS=1 <engine> <route-id> 2>&1 \
  | grep '^PROP ' | sort > /tmp/props_<engine>.txt
diff /tmp/props_c.txt /tmp/props_r.txt
```

Every value matches: `latency=2000`, `mode=CALLER`, `auto-reconnect=true`,
`keep-listening=false`, `poll-timeout=1000`, `wait-for-connection=true`, identical
`uri`, `do-timestamp=false`, `typefind=false`. The only differences are rendering
(`TRUE` vs `true`, quotes, type prefixes) and `passphrase`, which the Rust skips
because it is write-only and reading it panics.

### Connection order: ruled out

Swapping the launch order (Rust first, C five seconds later, live Test route stopped)
keeps the result attached to the engine, not the order:

```
Rust (connected first)  recv=202183  lost=3609  dropped=48  retrans=3535  1.79%
C    (connected second) recv=197370  lost=0     dropped=0   retrans=0     0%
```

So the source does not favour its first caller. The Rust engine loses SRT packets
whatever the order; the C engine does not. Next diagnostic: dump both pipelines
(`GST_DEBUG_DUMP_DOT_DIR`) and diff the element graph, since element properties, config
and libraries are now all proven identical.

Practical impact today: SRT recovers the loss (`retrans` ≈ `lost`), so the delivered
stream is intact (previews clean, no artifacts). The visible symptom is the loss
percentage / `warning` badge, not picture quality.

## Findings Worth Keeping

- **The engine's PIDs are correct for the stream it receives.** A temporary dump of
  the probe's first buffers showed a coherent PAT (`PID 0 → PMT PID 32`) and PMT
  (`video 65 / audio 66`); the capture of the same source with ffmpeg shows PMT PID
  4096 / video 256. The two streams also differ in style (the engine's PAT/PMT
  packets carry adaptation fields, ffmpeg's do not), i.e. the source serves a
  different mux per caller. Nothing to fix engine-side; check the source box.
- **`net.core.rmem_max` / `wmem_max` were 212992 (208 KB)** on this host, far below
  the 16 MB AGENTS.md requires for SRT at 9-50 Mbps — the likely cause of the
  `packets-received-dropped` / loss counters that pushed a local route into
  `warning` (Test: 5773 lost, 2783 dropped, 2924 retransmitted, RTT 0.48 ms).
  **Resolved:** raised to 16777216 and verified in effect (`sysctl` reads 16777216
  for both keys); the engines were restarted afterwards, so they run with the 16 MB
  buffers. All three routes now report `loss-window-pct` 0.0. The same two keys
  still need to be set on the source appliance (the ISO firstboot script does it).
- `make build` does build the engine: the release step `copy_native/1` in `mix.exs`
  runs `make -C native` and copies the binary into the release priv. A running app
  keeps the old engine until its routes are restarted.
