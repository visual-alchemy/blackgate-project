# 2026-10-17 Session 2 — duo2 Statistics Port to the Rust Engine (Video Metadata)

## Sprint Goal & Focus

Apply the statistics that exist on `feat/decklink-duo2` to the Rust engine, and
find out why the Dashboard showed no video metadata and why a purely local SRT
route reported degraded metrics.

## What Was Accomplished

### engine-metadata — four defects that hid every video statistic

- **PMT off-by-one.** After `section_length`, `parse_pmt` skipped four bytes
  instead of five (`program_number` 2 + version 1 + section_number 1 +
  last_section_number 1). `program_info_length` was therefore read one byte early
  (240 instead of 0 on a real stream) and the stream loop walked off the packet, so
  **every** PMT failed to parse: no `video-*` keys ever reached the UI. Regression
  tests use the real captured PMT packet plus a synthetic one whose audio PID
  follows the video PID.
- **500-attempt cap removed.** The port invented a per-TS-packet attempt limit and
  printed `VIDEO_STREAM_TYPE:unknown` when it expired. Neither the C nor the lite
  engine has such a limit, and at 15 Mbps the cap expired in ~50 ms — long before
  the first SPS/IDR of a mid-GOP join. The probe now keeps looking until the stream
  yields a header, exactly like C.
- **TS packet resync.** SRT payload boundaries do not line up with 188-byte TS
  packets, so a buffer can start mid-packet; the fixed stride then read a bogus
  PAT/PMT (a live route reported video PID 65/audio 66 from a PMT packet with PID 32
  and a 140-byte adaptation field). `resync_offset()` now finds the first sync byte
  whose next 188-byte step is also a sync — the C `source_ts_probe_callback`
  behaviour, with an extra guard so payload bytes equal to `0x47` are not mistaken
  for a boundary.
- **Emulation-prevention bytes.** H.264/HEVC encoders insert `00 00 03` so an RBSP
  can never contain a start code. The C strips them (`remove_emulation_prevention`)
  before bit parsing; the port did not, so every field after the first escape
  shifted — a live High-profile SPS with two EPBs reported a framerate of
  `2^24` (16777216) instead of 25 fps. Now applied to both the H.264 and HEVC SPS
  paths, covered by a test using that real SPS.
- **duo2 fields ported.** `VideoInfo` gained `fps_inferred`, `video_pid` and
  `audio_pids`; the H.264 parser defaults to 25/1 with `fps_inferred = true` (C
  behaviour, the UI renders inferred rates as `~25 fps`); the PMT parser collects
  every stream entry (no early return at the first video entry) so audio PIDs that
  follow the video PID are not lost.

### engine-stats

- Emits `video-pid` (only when known) and `audio-pids`, and reports
  `video-framerate-inferred` from the new `fps_inferred` field instead of inferring
  it from `fps_num == 0`.

### Elixir

- `unix_sock_handler.ex`: `stats_to_metrics/2` walked every list as if it held
  nested stats maps, so the new `audio-pids` list of integers raised
  `BadMapError` on every report (`Error processing stats: %BadMapError{term: 66}`,
  twice a second). It now recurses only into maps and emits scalars as metrics.
- `route_health.ex`: the `drops_per_sec` check on `sdi_video_stats` is gone (duo2
  parity). Those counts are `videorate` framerate-conversion drops, not hardware
  failures; real failures crash the pipeline and are handled by RouteHandler.

### Web

- `RouteStats.jsx`: video format summary line (`AVC VIDEO FORMAT … 1920×1080p/25 ·
  16:9 · Input 12.158 Mb/s`), Video PID and Audio PID tiles, Received/Lost packet
  tiles, and the duo2 tile names.
- `SystemPipelines.jsx`: uses `systemPipelinesApi.getDetailed()` (endpoint and API
  client already existed) and shows Route, live CPU, RSS, threads and state.
- `HealthBadge.jsx`: warning tooltip said `RTT > 150ms`; the backend threshold is
  300 ms (`@rtt_warning`).

## Findings Worth Keeping

- **The engine's PIDs are correct for the stream it receives.** A temporary dump of
  the probe's first buffers showed a coherent PAT (`PID 0 → PMT PID 32`) and PMT
  (`video 65 / audio 66`); the capture of the same source with ffmpeg shows PMT PID
  4096 / video 256. The two streams also differ in style (the engine's PAT/PMT
  packets carry adaptation fields, ffmpeg's do not), i.e. the source serves a
  different mux per caller. Nothing to fix engine-side; check the source box.
- **`net.core.rmem_max` / `wmem_max` are 212992 (208 KB)** on this host, far below
  the 16 MB AGENTS.md requires for SRT at 9-50 Mbps. That is the likely cause of the
  `packets-received-dropped` / loss counters that push a local route into
  `warning` (Test: 5773 lost, 2783 dropped, 2924 retransmitted, RTT 0.48 ms). Needs
  `sudo sysctl -w net.core.rmem_max=16777216 net.core.wmem_max=16777216` here and
  on the source appliance.
- `make build` does build the engine: the release step `copy_native/1` in `mix.exs`
  runs `make -C native` and copies the binary into the release priv. A running app
  keeps the old engine until its routes are restarted.
