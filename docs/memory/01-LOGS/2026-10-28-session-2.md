# Session 2 — 2026-10-28 (night)

Continues `2026-10-28-session-1.md`. Release `2026.10.28.1` is live and the SDI playout watchdog fix is proven
(2 freezes, both recovered on attempt 1/4, 0 abandoned, 0 flapping). The open defect was the per-engine memory
growth of roughly **+47 MB/h on every engine that decodes**, which ends in OOM after two to three days.

## The verdict in one line

The growth is not in the appliance. It is a per-frame leak inside **`gst-libav` 1.24.1**, the version Ubuntu
24.04 ships: about **233 bytes per decoded frame**. Moving the same pipelines to **1.26.6** removes it
(SDI-shaped branch: +94 MB → +6 MB over 15 minutes, curve flattening, CPU unchanged). Our engine binary runs
unmodified on 1.26 — GStreamer 1.x ABI holds.

## What closed the last hypotheses

**heaptrack is not usable on this pipeline.** Installed and exercised: it segfaults on the decode chain, and
the run that did not crash recorded only startup allocations (peak 1.12 MB while the process sat at 200 MB
RSS). Not a plan any more.

**Element bisect** (`decode-bisect.sh`, 240 s per arm, file loop, CPU 250-270%):

| arm | chain | result |
|---|---|---|
| D | `tsdemux ! h264parse ! fakesink` | 37 → 40 MB (+3 MB) — parser is clean |
| E | `tsdemux ! avdec_h264 ! fakesink` | dead, `preroll` fails: avdec needs parsed input |
| F | `... ! avdec_h264 max-threads=1` | 92 → 112 MB (+20 MB) — still grows, at half the rate |
| G | `... ! avdec_h264` (default threads) | 152 → 195 MB (+43 MB) |

Growth scales with decoder thread count, which is decoder-internal retention, not our pipeline.

**Other decoders on the box** (`decode-alt.sh`, 180 s per arm):

| decoder | result |
|---|---|
| `vaapih264dec` | 104 → 106 MB — flat, and output is **bit-identical** to avdec (same md5 over 805 frames) |
| `openh264dec` | 2004 → 3904 MB — far worse, rejected |
| `vulkanh264dec` | dead at `PAUSED` |

VA-API is closed as a product answer: the operator's constraint is that client boxes may have **no GPU**, so the
shipped fix must be CPU-only. It stays useful as evidence that the leak is specific to the libav software path.

## The proof, three layers

| layer | 1.24.2 | 1.26.6 |
|---|---|---|
| realtime decode, monotonic PTS, CPU only (`realtime-avdec.sh`, 900 s) | 70 → 75 MB (+5 MB) | 70 → 71 MB (+1 MB) |
| SDI-shaped branch, file loop at full speed (`sdi-branch-probe.sh`, 900 s) | 184 → 278 MB (+94 MB, linear to the end) | 187 → 193 MB (+6 MB, flattening) |
| realtime decode, 2 hours (`realtime-avdec.sh`, 7200 s) | — | **71 → 71 MB, 0.00 MB/min** |
| engine binary (`engine-gst-ab.sh`, 1200 s) | 82 → 82 MB | 80 → 83 MB |

The engine arm proves the binary runs on 1.26 (`/proc/<pid>/maps` shows `libgstreamer-1.0.so.0.2606.0`, the
decode branch is built, `SOURCE_VALID=1`, the receiver gets video) — but it does **not** reproduce the leak,
because the `preview` branch is a thumbnail decoder, not the SDI branch. A true engine-level SDI test needs a
DeckLink device; all four are held by live routes:

## Running a newer GStreamer without touching the box

The prefix recipe that worked, and every trap in it, because none of it is obvious:

1. Fetch packages with a **private apt sandbox** (`Dir::Etc::sourcelist`, `Dir::State`, `Dir::Cache` pointed at
   the prefix, `questing` only — not `questing-updates`, which drags libc 2.42 and systemd 257).
   `apt-get install` resolution is useless here: it plans to upgrade all of glibc. Use `apt-get download` per
   package.
2. Needed: `gstreamer1.0-{libav,plugins-base,plugins-good,plugins-bad,tools}`, `libgstreamer1.0-0`,
   `libgstreamer-plugins-base1.0-0`, `libgstreamer-plugins-{bad,good}1.0-0`, plus ffmpeg 7.1
   (`libavcodec61`, `libavformat61`, `libavutil59`, `libavfilter10`, `libswscale8`, `libswresample5`).
3. `gst-plugin-scanner` needs the shared libs that live **in `libgstreamer-plugins-bad1.0-0`, not in the plugin
   package** — without them `libgstcodecparsers-1.0.so.0` and `libgstmpegts-1.0.so.0` resolve to noble's 1.24
   copies and the mpegts demux fails with `undefined symbol`.
4. GStreamer 1.26 needs **glib ≥ 2.81** (`g_sort_array`); noble has 2.80. Pull `libglib2.0-0t64` (2.86) into
   the prefix too.
5. ffmpeg 7.1 links newer codec libraries (`libjxl0.11`, `librav1e0.7`, `libsvtav1enc2`, `libx265-215`,
   `libplacebo349`, `libpostproc58`, `libxml2-16`) and **libva ≥ 2.21** (`vaMapBuffer2`); noble has 2.20.
6. Total: ~40 packages, 132 MB extracted under `~/gst126/root`, system untouched.
7. **Delete the registry** whenever the prefix changes. A registry written while a plugin was unresolvable keeps
   reporting it missing; `multifilesrc` "did not exist" for exactly this reason.

## The version landscape this creates

| basis | gst-libav | note |
|---|---|---|
| Ubuntu 24.04 (current) | 1.24.1 | leaks, measured |
| Debian 13 trixie | 1.26.2-1+deb13u1 | **older than the version we proved** (1.26.6) — needs its own 15 min run before it can be trusted |
| Ubuntu 26.04 LTS "Resolute Raccoon" (23 Apr 2026) | 1.28.x | newer than proven; DeckLink is officially supported; LTS to 2031 |

Consequence: Debian 13's size advantage shrinks to tens of megabytes once the image is assembled from `minbase`
with a pruned package manifest, while its driver risk (Blackmagic Desktop Video via DKMS on a 6.12 kernel,
unsupported distribution) does not shrink at all. The working recommendation is **Ubuntu 26.04 LTS with a
debloated, manifest-driven rootfs** — not dist-upgrade, and not Debian.

Debloat levers, in order of size: `/usr/share/doc` + man + locales (150-250 MB), unused GStreamer plugins (we
need ~15 of 256), snapd/cloud-init/netplan/ubuntu-pro (~100 MB), unused firmware and kernel modules, and keeping
ffmpeg CLI out of the runtime image entirely (it is probe-only).

## Not proven yet

- 1.26.2 specifically (what Debian 13 would give us).
- The engine on the real SDI branch: needs a DeckLink device, i.e. stopping `52b09cb6` (device 1) for ~40 min,
  or the new box.
- DKMS `blackmagic` 16.4a1 against the 26.04 kernel. If that fails, the whole basis decision reopens.

## Harness traps added tonight

1. `num-buffers` on `multifilesrc` counts TS buffers, not frames: a "60 frame" md5 test wrote **33 GB** of raw
   video before it was killed. Bound by wall clock and divide by frame size (3,110,400 bytes for 1080p I420).
2. `pkill -f "filesink location=cmp-"` matched the calling shell and killed it (exit -15). Signal explicit pids.
3. An ffmpeg SRT listener serves exactly **one** caller; a second receiver arm starves silently.
4. The engine exits on stdin EOF — keep the writer alive past the last sample, or the final RSS reads as `?`.
5. File-loop results are **not** live rates: the 20 s loop restarts PTS and inflates growth ~13x.
6. A flat RSS with cpu 0% is a stalled pipeline; every probe now prints cpu or a frame count.
