# 2026-10-21 Session 1 — SDI output on the DeckLink Duo 2: interlaced feeds, a fatal sink, and a new branch

## Sprint Goal & Focus

Get real SDI output working on the installed Blackmagic DeckLink Duo 2 (4 usable outputs), keep the
live PLTV/SPOTV2 routes healthy while doing it, and leave the migration checkpoint untouched.

## What Was Accomplished

### DeckLink driver and card state

Desktop Video 16.4 installed; `BlackmagicFirmwareUpdater status` reports all four sub-devices
(`io0`–`io3`, FW 11-25 10:59). Port map restored from `feat/decklink-duo2`:
SDI 1 → device 0, SDI 2 → 2, SDI 3 → 1, SDI 4 → 3. All four outputs require
`profile=two-sub-devices-half`, which the engine now **pins per SDI sink** — a profile the card
cannot run fails the sink outright, so the "DeckLink Profile" selector was removed from the UI.
`net.core.rmem_max/wmem_max` = 16 MB survive reboot.

### Interlaced output did not work at all

PLTV's SDI output died every ~12 s. Three layers, all reproduced:

1. `decodebin` reports an interlaced H.264 feed as `interlace-mode=mixed`; the old check accepted
   only `interleaved`, so the chain demanded **1080p25** for a 1080i50 source.
2. Nothing can convert `mixed` into the `interleaved` caps an interlaced DeckLink mode demands —
   `videoconvert` refuses, and the `interlace` element cannot output UYVY on GStreamer 1.24. Proof
   with `gst-launch`: `NV12 mixed → videoconvert → capsfilter(interleaved)` fails, the same chain
   with a progressive source succeeds.
3. The error was **fatal** to the whole pipeline: `not-negotiated` stopped the SRT source's task,
   the engine exited, and RouteHandler reconnected forever — the SDI sink took the route's SRT
   output down with it.

Fixes: interlaced detection now treats anything except `progressive` as interlaced; the box's broken
VA decoders (`vah264dec` family — VA init fails here) are demoted at engine startup so decodebin
picks software `avdec_h264`, which is what negotiates. Result on the live PLTV feed:
`SDI AUTO-DETECT: MATCHED → mode=1080i50`, frames on the card, no reconnect.

### SDI audio

The C-era 2→8 upmix (`audiomixmatrix`, S16LE 8ch + mask 0xc3f) cannot negotiate against the AAC
decoder's `F32LE non-interleaved 2ch`. `decklinkaudiosink` accepts channels {2, 8, 16} with no
channel-mask, so the chain is now stereo end to end and the upmix is gone (kept in the library for a
deployment that genuinely needs 8 discrete channels).

### Diagnosability

Bus errors now print the failing element, its ancestry and GStreamer's debug string — the difference
between "Internal data stream error" and `element=decklinkvideosink1 … Failed to schedule frame`.
That is what made the two runtime failure modes reproducible at all.

### SDI sink failures no longer kill the route

`route_handler.ex` documents the contract: the engine warns
`WARNING: SDI sink N failed — continuing without SDI output` and keeps running. The Rust engine never
did that. It now attributes a bus error to an SDI branch by element identity, prints that marker,
detaches the branch from the tee (releases the tee pad, parks the DeckLink sinks at NULL) and keeps
the run loop alive; source/SRT/thumbnail/pipeline errors stay fatal so reconnect still works.
Boundary: an SDI failure at *negotiation* time (e.g. another process holds the card) still ends the
run — its error is reported by the source element, whose task is already dead.

### UI: target the Duo 2, not the Quad 2

Video Mode dropdown no longer offers 2160p/4K, interlaced modes are labelled with their real
frame/field semantics (`1080i50 — 25 fps / 50 fields`), and the mode maps in the output popover and
the routes table match `feat/decklink-duo2` exactly.

### Verification

Rust: fmt clean, clippy `-D warnings` clean, workspace tests green (engine-gst now 6 tests: SDI
branch attribution, branch detach on a real pipeline, RouteHandler marker contract). Live: PLTV and
SPOTV2 play 1080i50 with 0 dropped / 0 duplicated and audio flowing; per-engine CPU ~0.8 core and
~0.5 core. A 12–24 h resource monitor is recording to `~/blackgate-trend/`.

### Settings > System, phase 1 (read-only)

`feat(system)`: a System tab showing what the host actually is — hostname, OS, kernel, uptime,
memory, disk, the UDP socket buffers against the documented 16 MB, the DeckLink devices, the engine
binary with its sha256, the service unit's state, and per-route health plus SDI video stats labelled
with the same device-to-jack map the destination form uses. `GET /api/system/report` returns the same
facts as a plain-text download, Blackmagic's firmware view included. Verified end to end against the
running release: HTTP 200 on both endpoints, real values throughout.

What the new report taught us:

- `make build` **rebuilds the engine from source and copies it into the release** (`mix.exs`
  `copy_native/1`), so an engine change ships with the next build — the manual
  `cp native/build/blackgate-engine priv/native/build/` step I handed over earlier is unnecessary.
- Blackmagic's own tool enumerates the card as sub-device 0 → `io0`, 1 → `io2`, 2 → `io1`,
  3 → `io3`. If that index is the SDK `device-number` the engine uses, then device 1 is connector 2
  (SDI 2) and device 2 is connector 3 (SDI 3) — the opposite of the map inherited from
  `feat/decklink-duo2`. The physical label test settles it, and devices 0 and 2 are free for it.
- `make restart` leaves the routes **stopped**: a clean shutdown writes `stopped` into Khepri and
  nothing resumes them at boot. PLTV and SPOTV2 had to be started by hand afterwards. This is the
  reboot-resume gap from the open items, and it applies to a plain restart too.

### Settings > System, phases 2 and 3 (actions and signed updates)

`feat(system)`: the tab can now restart, reboot, shut down and deploy — and the appliance has a real
update path. The privileged surface stays one allowlisted helper: `blackgate-system-action` schedules
every action as a delayed transient systemd unit (restart 3 s, reboot/shutdown 10 s, deploy 2 s), which
is what makes cancel possible and "what is scheduled" answerable. A `test-action` proves sudoers +
systemd-run without rebooting anything. `blackgate-updater` verifies the Ed25519 manifest signature and
the release checksum, swaps the `current` symlink atomically, and rolls back by itself when the new
release fails its health check. Packages are built by `scripts/package-signed-update.sh`, which bakes
`priv/release-notes.json` into the release so the dashboard knows which release is running.

Credentials moved out of the unit file (world readable) into `/etc/blackgate/blackgate.env`, 0600 root;
the unit now runs `$ROOT/current` so a deploy never edits it. One installer
(`scripts/install-system-actions.sh`) sets all of it up, and the ISO's first boot calls that same
installer instead of duplicating the logic. Without the helper and sudoers the dashboard disables the
buttons and says why, rather than offering a button that fails.

Open items this raised or moved:

- The routes are stopped right now because the gateway was stopped by hand; nothing resumes them
  automatically (see the Khepri-resume item below). Their state is otherwise untouched.
- Moving this box to a systemd-managed deployment root changes the daily workflow: after that, changes
  ship as packages (`scripts/package-signed-update.sh` → upload → deploy) instead of `make build` +
  `make start`. Both layouts can coexist, but only the deploy root is what the unit and the updater
  manage.
- The ISO still does not carry the Blackmagic Desktop Video `.deb`, so a fresh appliance has the
  GStreamer DeckLink plugin but no driver.

### Deploying to a real systemd unit: what actually broke

Installing the integration on the live box surfaced three faults the appliance layout had been hiding,
all fixed in the unit and the installer:

- `/usr/local/libexec` does not exist on Ubuntu 24.04; the installer assumed it did.
- `Environment=ERL_AFLAGS=-proto_dist inet_tcp` was unquoted. systemd splits an Environment value on
  whitespace, so ERL_AFLAGS became `-proto_dist` and the rest was dropped as an invalid assignment.
- `RELEASE_DISTRIBUTION=none` (inherited from the branch) makes the node anonymous. Khepri's store
  records the node in its Ra membership and `bin/blackgate rpc`/`pid` need distribution, so the gateway
  came up on a **fresh empty database** — the journal said `0 record(s) recovered` — while the routes sat
  untouched in `khepri#blackgate@blackgate`. The unit now sets `RELEASE_NODE=blackgate`, and the
  installer refuses a `--data-dir` that is the *parent* of a store rather than the store itself.

Verified live afterwards: PLTV (device 1) and SPOTV2 (device 3) healthy at 1080i50, 0 dropped/duplicated,
SDI audio flowing; `POST /api/system/updates` uploads a package into the deployment root (HTTP 201, and a
non-gzip body is refused with 422); `POST /api/system/actions/restart_gateway` schedules
`blackgate-dashboard-restart.timer`, the status endpoint reports it (with its fire time), and `cancel`
stops it before it runs — the node's PID is unchanged, so the whole sudoers + systemd-run + `sudo -n`
chain works. Scheduled actions appear in Events as `system_action`, now with guidance text.

Also: an earlier commit in this session (`git add -A`) swept an empty Khepri store into the repository
while the wrong `DATABASE_DATA_DIR` had dropped it in the project root. Removed, and `.gitignore` now
ignores `*.dets`, `*.wal` and `/KHEPRI*/` — those files are someone's routes, not source.

## Signed updates, verified end to end (written after the sections above)

The box now deploys from `/opt/blackgate` (repo unchanged at `/home/blackgate/blackgate-project`), and
the whole update path has been run with root: upload `201` → deploy `202` → `deploying: <v>` → atomic
`current` symlink swap → service restart → `deployed: <v>`, plus a **genuine downgrade** (deploy an older
version whose `.bgupdate` is still retained, which is the only way a version can be reactivated) and a
return to the newest. Three releases are retained.

Both safety nets are proven by fault injection, not by reading the code:

- A package signed with the WRONG key is refused with `failed: signature verification failed`; the running
  release stays put and the service PID does not change, so a forged package cannot touch the gateway.
- A deliberately broken release (`bin/blackgate` not executable, correctly signed) hits the health check
  and rolls back automatically.

That second test found a real defect: `systemctl restart` on a unit that keeps failing under
`Restart=always` does not return until systemd gives up (~90 s), so the health check — and the rollback —
only ran after that, leaving the gateway in `activating` the whole time. The updater now bounds the wait at
25 s and the same fault rolls back in ~10 s ("deployed" → 10 s → `failed: new release failed; rolled
back`, `current` back on the previous release, service active on a new PID). The retained package for the
running version was re-cut afterwards so a rollback cannot reinstall the old updater.

Also fixed while proving this: `make build` retries the release assembly once (`Mix.Release.copy_erts`
race, hit three times), the packaging script strips `--no-build` before the positional arguments, it hands
the release-notes file back to the invoking user after a `sudo` run, and `dist/*.bgupdate` is no longer
tracked (`git add -A` had swept a 28 MB package into a commit; the blob stays in history).

Deploying a release stops every route, and a deploy costs a ~40 s `deploying` window plus the restart, so
plan the SDI downtime — the routes were started again by hand afterwards and both came back healthy.

## Open Items

- **Non-fatal SDI fix**: engine `19cbe111ef995bb3` is what the release runs now — `make build` rebuilds
  and ships the engine, so it went live with the System build. Its live behaviour (a route surviving a
  failing sink, with the warning and the `sdi_failed` event) is still unverified: PLTV HDR is the
  reliable trigger and has not been run since.
- **PLTV HDR (H.265 1080p50)**: starves the sink — ~10 fps reach it for a 50 fps mode, ~7 drops/s,
  then "Failed to schedule frame" every ~40 s. Software HEVC 50p costs ~2.6 cores. Not mandatory;
  parked.
- **`do-timestamp=TRUE`** is set for any route with an SDI sink; the 2026-06-10 log blamed exactly that
  for `Failed to schedule frame` on remote feeds. Worth a decision.
- **iso-builder does not install Desktop Video** (only the GStreamer plugin and the sysctl buffers),
  so a fresh appliance has no SDI until the driver is installed by hand — and no ISO has been built with
  this session's new files (unit, helpers, firstboot) at all.
- **Reboot from the appliance path is untested** (the dashboard's restart action is proven; `systemctl
  reboot` on this box is not), as is the dashboard's own UI surface beyond the endpoints behind it.

Settled by the operator — do NOT re-raise these as findings:

- **The device→connector map is intentional.** `DEVICE_TO_SDI {0:1, 1:3, 2:2, 3:4}`: device 1 = SDI 3 is
  deliberate, chosen so the SDI outputs run in physical order. The firmware report's `0→io0, 1→io2, 2→io1,
  3→io3` reading is not a discrepancy to resolve and no label probe is needed — the operator confirmed the
  wiring, which closes the "physical device↔BNC label check" this log previously listed as pending.
- **Routes stay stopped after a reboot, on purpose.** The operator wants a fresh machine with nothing
  running after a restart, so there is no auto-resume to implement and Khepri recording `stopped` on a
  clean shutdown is the intended state, not a gap.
- **Four routes with four SDI outputs run simultaneously without trouble** (operator-run).
- **This box is a disposable test machine** that will be uninstalled, so no password rotation or other
  hardening follow-up is wanted.
