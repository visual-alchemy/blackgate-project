# 2026-10-21 Session 1 — SDI output on the DeckLink Duo 2: interlaced feeds, a fatal sink, and a new branch

## Sprint Goal & Focus

Get real SDI output working on the installed Blackmagic DeckLink Duo 2 (4 usable outputs), keep the
live PLTV/SPOTV2 routes healthy while doing it, and leave the migration checkpoint untouched.

## What Was Accomplished

### DeckLink driver and card state

Desktop Video 16.4 installed; `BlackmagicFirmwareUpdater status` reports all four sub-devices
(`io0`–`io3`, FW 11-25 10:59). Port map restored from `feat/decklink-duo2`:
SDI 1 → device 0, SDI 2 → 2, SDI 3 → 1, SDI 4 → 3. All four outputs require
`profile=two-sub-devices-half`, which the engine now **pins per SDI sink** — a profile the card
cannot run fails the sink outright, so the "DeckLink Profile" selector was removed from the UI.
`net.core.rmem_max/wmem_max` = 16 MB survive reboot.

### Interlaced output did not work at all

PLTV's SDI output died every ~12 s. Three layers, all reproduced:

1. `decodebin` reports an interlaced H.264 feed as `interlace-mode=mixed`; the old check accepted
   only `interleaved`, so the chain demanded **1080p25** for a 1080i50 source.
2. Nothing can convert `mixed` into the `interleaved` caps an interlaced DeckLink mode demands —
   `videoconvert` refuses, and the `interlace` element cannot output UYVY on GStreamer 1.24. Proof
   with `gst-launch`: `NV12 mixed → videoconvert → capsfilter(interleaved)` fails, the same chain
   with a progressive source succeeds.
3. The error was **fatal** to the whole pipeline: `not-negotiated` stopped the SRT source's task,
   the engine exited, and RouteHandler reconnected forever — the SDI sink took the route's SRT
   output down with it.

Fixes: interlaced detection now treats anything except `progressive` as interlaced; the box's broken
VA decoders (`vah264dec` family — VA init fails here) are demoted at engine startup so decodebin
picks software `avdec_h264`, which is what negotiates. Result on the live PLTV feed:
`SDI AUTO-DETECT: MATCHED → mode=1080i50`, frames on the card, no reconnect.

### SDI audio

The C-era 2→8 upmix (`audiomixmatrix`, S16LE 8ch + mask 0xc3f) cannot negotiate against the AAC
decoder's `F32LE non-interleaved 2ch`. `decklinkaudiosink` accepts channels {2, 8, 16} with no
channel-mask, so the chain is now stereo end to end and the upmix is gone (kept in the library for a
deployment that genuinely needs 8 discrete channels).

### Diagnosability

Bus errors now print the failing element, its ancestry and GStreamer's debug string — the difference
between "Internal data stream error" and `element=decklinkvideosink1 … Failed to schedule frame`.
That is what made the two runtime failure modes reproducible at all.

### SDI sink failures no longer kill the route

`route_handler.ex` documents the contract: the engine warns
`WARNING: SDI sink N failed — continuing without SDI output` and keeps running. The Rust engine never
did that. It now attributes a bus error to an SDI branch by element identity, prints that marker,
detaches the branch from the tee (releases the tee pad, parks the DeckLink sinks at NULL) and keeps
the run loop alive; source/SRT/thumbnail/pipeline errors stay fatal so reconnect still works.
Boundary: an SDI failure at *negotiation* time (e.g. another process holds the card) still ends the
run — its error is reported by the source element, whose task is already dead.

### UI: target the Duo 2, not the Quad 2

Video Mode dropdown no longer offers 2160p/4K, interlaced modes are labelled with their real
frame/field semantics (`1080i50 — 25 fps / 50 fields`), and the mode maps in the output popover and
the routes table match `feat/decklink-duo2` exactly.

### Verification

Rust: fmt clean, clippy `-D warnings` clean, workspace tests green (engine-gst now 6 tests: SDI
branch attribution, branch detach on a real pipeline, RouteHandler marker contract). Live: PLTV and
SPOTV2 play 1080i50 with 0 dropped / 0 duplicated and audio flowing; per-engine CPU ~0.8 core and
~0.5 core. A 12–24 h resource monitor is recording to `~/blackgate-trend/`.

### Settings > System, phase 1 (read-only)

`feat(system)`: a System tab showing what the host actually is — hostname, OS, kernel, uptime,
memory, disk, the UDP socket buffers against the documented 16 MB, the DeckLink devices, the engine
binary with its sha256, the service unit's state, and per-route health plus SDI video stats labelled
with the same device-to-jack map the destination form uses. `GET /api/system/report` returns the same
facts as a plain-text download, Blackmagic's firmware view included. Verified end to end against the
running release: HTTP 200 on both endpoints, real values throughout.

What the new report taught us:

- `make build` **rebuilds the engine from source and copies it into the release** (`mix.exs`
  `copy_native/1`), so an engine change ships with the next build — the manual
  `cp native/build/blackgate-engine priv/native/build/` step I handed over earlier is unnecessary.
- Blackmagic's own tool enumerates the card as sub-device 0 → `io0`, 1 → `io2`, 2 → `io1`,
  3 → `io3`. If that index is the SDK `device-number` the engine uses, then device 1 is connector 2
  (SDI 2) and device 2 is connector 3 (SDI 3) — the opposite of the map inherited from
  `feat/decklink-duo2`. The physical label test settles it, and devices 0 and 2 are free for it.
- `make restart` leaves the routes **stopped**: a clean shutdown writes `stopped` into Khepri and
  nothing resumes them at boot. PLTV and SPOTV2 had to be started by hand afterwards. This is the
  reboot-resume gap from the open items, and it applies to a plain restart too.

## Open Items

- **Non-fatal SDI fix**: engine `19cbe111ef995bb3` is what the release runs now — `make build` rebuilds
  and ships the engine, so it went live with the System build. Its live behaviour (a route surviving a
  failing sink, with the warning and the `sdi_failed` event) is still unverified: PLTV HDR is the
  reliable trigger and has not been run since.
- **PLTV HDR (H.265 1080p50)**: starves the sink — ~10 fps reach it for a 50 fps mode, ~7 drops/s,
  then "Failed to schedule frame" every ~40 s. Software HEVC 50p costs ~2.6 cores. Not mandatory;
  parked.
- **Route auto-resume after reboot**: Khepri records `stopped` on clean shutdown and nothing resumes
  routes at boot. Declined for now (operator starts them by hand).
- **`do-timestamp=TRUE`** is set for any route with an SDI sink; the 2026-06-10 log blamed exactly that
  for `Failed to schedule frame` on remote feeds. Worth a decision.
- **iso-builder does not install Desktop Video** (only the GStreamer plugin and the sysctl buffers),
  so a fresh appliance has no SDI until the driver is installed by hand.
- **Settings > System** (as on `feat/decklink-duo2`): feasibility reviewed — status panel is safe and
  can be richer than theirs (per-route `sdi_video_stats`); restart/reboot actions need a systemd unit,
  the sudoers helper and appliance packaging.
- Physical device↔BNC label check still pending; `~/sdi-label-check.sh` cycles a distinct test pattern
  per sub-device for that.
